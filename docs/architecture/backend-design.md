# Backend Design

IP-005 · Stage 02 COMPLETED AND APPROVED · [AD-001, AD-002](adr/adr-001-modular-runtime.md) · [AD-006–AD-009](adr/adr-003-background-processing.md)

## Module boundaries

`backend/src/infrapulse/` is the import root. `api/v1/` composes routers and request dependencies. `tasks/` exposes Celery entrypoints and routes. `core/` provides settings, database factories, logging, clock and outbound policy primitives. `backend/migrations/` owns Alembic revisions and `backend/tests/` holds unit, integration and controlled system fixtures.

| Module | Owns | Depends on |
|---|---|---|
| `users` | Account identity and self read model | Core |
| `auth` | Bootstrap, credentials, JWT and refresh families | Users, workspace creation service |
| `workspaces` | Ownership, workspace settings and tenant context | Core, account identity reference |
| `monitors` | Configuration, lifecycle, schedule cursor and streaks | Workspace scope |
| `checks` | Reservations, outbound execution, history, scheduler | Monitor service, outbound policy |
| `incidents` | Threshold evaluation, transitions and retained history | Scoped monitor/check values passed by caller |
| `notifications` | Channel lifecycle, delivery creation and Telegram adapter | Workspace scope and immutable incident transition |
| `metrics` | Read-only dashboard and observation metrics | Scoped read interfaces of monitors, checks, incidents |

API and task entrypoints call services or transaction coordinators. Schemas describe boundary DTOs, models describe shared SQLAlchemy mappings, repositories contain scoped queries where reuse warrants them, and services enforce rules. The coordinators own commit/rollback. Repositories do not commit. Cross-module writes use services within one unit of work. Integrations consume durable references and reload trusted state. Alembic imports the unified metadata through a composition root.

FastAPI uses one async engine and session factory per process, with one session per operation. Celery prefork children initialize independent sync DB, broker and HTTP resources after fork. Control publication uses its own bounded RabbitMQ channel. Disposable probe connections are per execution. No child inherits a live pool, socket or lock descriptor from a parent. Explicit rollback and close happen on error. DB sessions are released before external calls, and reopened for settlement. Pool limits and connection headroom are measured with API/control budgets protected against worker saturation.

## Scheduling and reservation

- Beat sends bounded control ticks every second as an initial tuning choice. A single Beat simplifies tick production. Route guard recovery ticks to the check pool. The control pool has no access to guard files and never reclaims a running probe. Duplicate or lost ticks are tolerated. Ticks are short-lived and separate from durable business jobs.
- The dispatcher processes due active monitors ordered by `(next_check_at, id)` in bounded batches using `FOR UPDATE SKIP LOCKED`. Under the monitor lock it reserves one scheduled execution and its outbox job, updates the schedule cursor, and commits. Schedule slots are anchored to configured cadence, independent of completion. Initial, resumed and interval-edited cadences start a new epoch with first due time within one interval. Validate spreading of concentrated due times.
- Advance to the first future slot on each dispatch. For multiple due slots, record older skipped slots as compact ranges and consider only the latest due slot. A queued scheduled execution expires at the following slot boundary. Record skipped busy slots when an active reservation occupies the monitor, including a manual execution that spans the due time. Never run a historical backlog of probes.
- Manual acceptance locks the same monitor row. Active, authorized, idle monitors get a MANUAL reservation and outbox item in one transaction. Persist `last_manual_accepted_at` using database time in that transaction. Reject a paused or busy monitor with 409 and a rate violation with 429, without accepting a reservation or moving its schedule. Initial manual queue deadline is two minutes for operational tuning. A due time crossed during a manual run remains a scheduled slot with its own disposition. When handling an eligible slot after a manual job has settled, the dispatcher also checks for any scoped manual reservation interval covering that due time, from acceptance through settlement. The current active reservation remains a separate collision check.
- The active-execution unique index enforces one nonterminal reservation per monitor. A schedule cursor and unique scheduled slot key prevent duplicate scheduling. Worker progress states use QUEUED, RUNNING, COMPLETED, SKIPPED and INTERRUPTED. COMPLETED includes the observation outcome. A missed opportunity has a disposition and no check result; pause intervals remain separate. Use execution timestamps and reason codes for delay and failure diagnostics.

## Worker execution and exclusion

The MVP runs all probe workers on one Linux host. Under [AD-014](../project/decision-register.md#ad-014), one check-worker container runs multiple prefork children. A subsequent execution requires evidence that the previous local execution has ended, and lease expiry alone cannot authorize it. Its children share a host-local OS execution lock for each monitor UUID and a separate start lock for lifecycle serialization. The shared lock storage and single-host constraint are part of [ADR-005](adr/adr-005-outbound-and-deployment.md). A connected HTTP peer may continue server-side work after the client closes; the exclusion applies to InfraPulse-owned network activity.

1. A check child takes the exclusive execution lock before preparing a probe or reclaiming an expired run. If busy, acknowledge a duplicate wakeup or defer reconciliation. A contender may never dial on the strength of a lease. Lock ownership survives a PostgreSQL disconnect, scheduler failure, and lease expiry.
2. In a short transaction lock monitor then execution, verify tenant, monitor state and version, execution generation and queue deadline; set RUNNING, lease expiry and attempt token. Resolve and validate DNS under the exclusive execution lock with a separate bounded preparation budget. Preparation failures settle as ERROR with safe diagnostics.
3. Acquire the per-monitor start lock, reload and verify state/version/token again, and commit an irreversible `network_start_marked_at` and the owning process incarnation before dialing. Hold the start lock through numeric connection, TLS and initial HTTP request write. Release at the confirmed write boundary or after closing a failed socket. Pause, resume, edits and deletion acquire this same start lock through their lifecycle commit. This serializes actual outbound starts with lifecycle changes even if a database connection disappears. A queued job that loses the race to pause cannot dial. Use a bounded async lock wait in API handlers, aborting without partial mutations on timeout. No retry, redirect or reconnect follows the initial dial.
4. Start the configured monotonic target budget at the approved numeric dial. Read response headers within the time left after connect, TLS and request write. Capture UTC completion at observed completion or classification, before waiting for result settlement. Use synchronized host UTC and retain monotonic latency separately. Record actual dial timing for schedule delay evidence; the initial durable start marker is only a recovery fence. Close the transport and settle using a new DB transaction and attempt token while still holding the execution lock. Release the lock after settlement commits or the attempt is abandoned. On failed or ambiguous settlement of a marked attempt, retire the child if it cannot durably confirm closure/settlement, so supervisor exit evidence can unblock guarded recovery. A crash after marking start can leave no valid observation. Recover under that same execution lock. For a marked attempt, also require evidence that the former local client closed its socket or its exact process incarnation fully exited. A lock becoming available during process teardown is insufficient evidence by itself. If still eligible, retry only a pre-start execution within its deadline, up to two claims in total. A marked attempt with no committed result becomes INTERRUPTED without reissuing its request. Expiry while the socket is live is a diagnostic and never bypasses the lock.
5. An active job invalidated by a lifecycle change retains its reservation through settlement or guarded recovery. A stale in-flight result may be retained as diagnostic history for a live monitor. Tombstoned monitors reject all subsequent history writes. Queued work invalidated by lifecycle changes may be settled SKIPPED under the monitor row lock when there is no active start.

Use a unique worker-container generation and a per-child incarnation ID, with the prefork supervisor observing exact child exit/reap. For a container restart, permit recovery of prior-generation owners only after the host confirms the prior container and all its descendants have stopped. Unknown ownership or lost exit evidence leaves the reservation fenced and alerts the operator. Process IDs alone can be reused. The proof gates recovery and any subsequent probe of the monitor.

Lock order is execution lock → start lock where needed → monitor row → execution row. Lifecycle operations start with the start lock. Dispatcher and pure DB processors use DB locks only. Reconciliation uses nonblocking execution-lock acquisition before SQL. Lease sweeps use bounded queries and revisit live owners. Reconciliation clears abandoned active reservations only after guard acquisition, including RUNNING rows made ineligible by edits or pause. Hold descriptors in the actual prefork child that owns the socket and never transfer them or delegate network I/O to a surviving subprocess. Use bounded phase operations and a hard process deadline covering preparation, the target deadline and settlement grace; OS cleanup releases locks on process death. Decommissioning the host requires proof that old check processes and sockets are gone before any replacement host can run probes.

## Outbox and message recovery

Create outbox rows in the same transaction as check reservations, durable incident transitions and eligible retry decisions. Rows carry a stable logical check, incident transition or delivery reference, an outbox UUID, routing type and generation. Publish durable messages to durable queues with publisher confirms and mandatory routing. Mark published only after a positive confirm and routing success. A returned unroutable message, nack or ambiguous channel failure leaves the row eligible for retry. Keep published rows long enough for reconciliation and diagnostics. Worker messages contain IDs, neither configuration nor secrets.

Control ticks drive independent dispatch, relay and reconciliation passes, with bounded batches and dedicated capacity for each pass. The relay claims bounded batches via `SKIP LOCKED` and a persisted time-limited claim token, spends an attempt before commit, publishes outside the transaction, then settles with that token. On ambiguous publication it may emit the same message again. Initial automated budget is five publication attempts with jittered backoff (1, 2, 4, 8 seconds before successive retries), capped by the business deadline where applicable. Exhaustion quarantines the row and emits an operator diagnostic. Repair routing and replay the same outbox row through an operator action after verifying the business state is still eligible. Expire overdue checks separately.

Consumers use late acknowledgements, low prefetch and explicit handling of worker loss. Commit before acknowledgement. A redelivery after commit observes the durable disposition and returns without effects. A crash before settlement leaves a DB reservation to reconcile. Use bounded DB-scheduled retries with a new wakeup generation, and reconcile missing deliveries from authoritative QUEUED/PENDING rows after an age threshold, within the same job-wide publication budget, which survives generation changes. Allocate that budget transactionally. The same logical job ID survives re-publication. Use durable quorum work queues with a configured finite delivery limit and durable dead-letter queues for exhausted or invalid messages. Verify the selected dead-letter delivery mode and broker behavior on the pinned stack. One broker host provides crash recovery with its persistent volume. Reconcile dead letters with DB state before operator replay. A poisoned envelope is rejected, and a known transient failure is acknowledged only after a durable retry decision or routed through bounded broker redelivery if PostgreSQL is unavailable. Check and notification queues are independent. PostgreSQL decides work and effects, RabbitMQ may deliver duplicates, and Redis holds no business state.

## Incident engine

The worker locks monitor then execution and validates scope, attempt token and terminal state. In one transaction it inserts the canonical observation, applies a live-state decision and opens or closes the incident where eligible. Persist each effective incident transition and its outbox event in that transaction, with any eligible delivery reservation. Lifecycle commands use the same transition writer for administrative closures. Same-execution replay is a no-op. Live decisions require a scheduled observation with matching configuration version, newer monitor sequence than the last applied qualifying observation, and a live non-PAUSED monitor. Keep eligible historic evidence for stale completions once, flag its exclusion from live state and metrics, and preserve the original version and origin. Manual results never enter the decision. A DB unique index enforces one open incident per monitor.

- A qualifying failure or target TIMEOUT advances the failure streak and resets the success streak. A qualifying success resets the failure streak and advances recovery when an incident is open. A first qualifying success for a PENDING monitor without a retained incident sets UP. At the failure threshold set DOWN and open an incident only if one is absent. An already open incident closes only at the recovery threshold, including after resume; a renewed failure threshold restores DOWN without opening another incident.
- Pause preserves the open incident and resets streaks. Resume enters PENDING. Every effective configuration edit resets streaks and increments the version. Ordinary edits retain live state and incidents. A checked-address edit on an active monitor sets PENDING and closes any open incident as CONFIGURATION_CHANGED. Under [PD-016](../project/decision-register.md#pd-016), a checked URL edit while PAUSED remains in PAUSED, closes any open incident as CONFIGURATION_CHANGED, resets both streaks and increments the configuration version in the lifecycle transaction. Keep dispatch suspended and start no automatic check. A later Resume enters PENDING. Deletion closes an open incident as MONITOR_DELETED. Only a confirmed recovery creates Incident Resolved delivery work.
- ERROR, SKIPPED, stale and manual work leave both streaks intact. Only qualifying ordered scheduled observations contribute. Use positive integer thresholds with defaults 3 and 2 and no additional product bound; validate representation limits and saturate counters at applicable thresholds.
- Use database time for schedule and lifecycle timestamps; monotonic execution timing separates preparation, transport and settlement. A healthy connection/response exceeding its target deadline is TIMEOUT. Unexpected status, attributable refusal and target certificate validation failure are FAILURE. Policy denial, ambiguous DNS/network failures, local resource exhaustion and worker interruption are ERROR or non-observation dispositions. A crash or queue delay cannot synthesize target TIMEOUT. The check evaluates the final response headers, with bounded header processing, and closes without downloading a response body.

## Notification engine

Use one Telegram configuration per workspace for MVP. At transition time, atomically snapshot the enabled channel version and destination identity and insert a unique PENDING delivery per logical transition and recipient. The notification worker consumes the incident transition wakeup and loads its persisted eligible delivery. A transition with no eligible delivery completes without an external call. Retries and recovery wakeups use a concrete delivery reference. Incident Opened and Incident Resolved are enabled by default. The unique key uses the immutable transition ID and a keyed digest over the canonical destination identity, independent of credential rotation. Revalidate current tenant, configured channel, version, enabled flag and event preference before reserving a send. Do not redirect old delivery work to a changed recipient. Settings changes prevent later reservations with invalid configurations. A reservation already committed for the old settings can have started externally; this boundary is visible in delivery disposition.

Lock the channel then the delivery, revalidate the configuration inside the reservation transaction, and reserve PENDING → PROCESSING with attempt token, deadline and attempt count and commit before any call. Only the owner of that attempt calls the provider. A concurrent duplicate observes PROCESSING and exits. Use one HTTPS request to the fixed provider through restricted egress, with a bounded total deadline (initially 10 seconds) and no implicit retries. Persist the result by compare-and-set on PROCESSING and attempt token before acknowledging:

| Disposition | Evidence and action |
|---|---|
| SENT | Positive provider acknowledgement, persist safe receipt reference and settle once. |
| FAILED | Permanent confirmed rejection, changed configuration before reservation, or exhausted eligible retries. Record a safe diagnostic. |
| PENDING | Confirmed non-delivery with retry eligibility, such as a supported rate-limit rejection or proven pre-send failure. Persist last error, retry time and next outbox wakeup. |
| UNKNOWN | Possible acceptance without durable proof, including post-send timeout, unclassified response, crash after provider acceptance or expired PROCESSING without settlement. Terminal for automated processing. |

Allow up to three sends/attempts total within ten minutes, with 10s then 60s initial backoff plus jitter. Honor a longer provider retry delay within the remaining window. Only explicit provider semantics or transport evidence of non-send permits retry. Reconciliation marks expired PROCESSING as UNKNOWN and settles an expired PENDING job as FAILED with a safe deadline diagnostic. Automated processing does not reopen either terminal disposition. A stale response cannot overwrite a terminal disposition. If the worker crashes before any send after reserving, this conservative policy can also result in UNKNOWN. Show confirmed failures and unresolved ambiguity independently of incident state.

For [AC-045](../product/acceptance-criteria.md#ac-045), hold a controlled successful provider response while the second handler enters processing, then confirm one matching recipient receipt. Separately replay after confirmed receipt and verify the count stays one. Test rejection, retry exhaustion and provider acceptance followed by a crash before SENT under [AC-046](../product/acceptance-criteria.md#ac-046).
